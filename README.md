# Whatcha · 在干嘛

One iPhone screen for a parent to ask 小乐, their child's AI agent, what the child is doing. M1 ports the Android WeChat-style text conversation to SwiftUI, iOS 17+, through the public relay. No menus or settings.

Open `Whatcha.xcodeproj`. A parent copies the child's 口令 from WeChat, returns to the app and taps the native 「粘贴」 button. The button is the system UIPasteControl, so the app reads text only after that tap and iOS asks no permission. The app saves the decoded pairing in UserDefaults and makes it permanent once the agent accepts the phone. A refused, unaccepted pairing returns to the paste screen for a fresh code and stops retrying. Accepted pairings cannot be replaced. The phone creates its own Ed25519 identity in Keychain on first launch.

For development, optionally copy `Config.example.xcconfig` to `Config.xcconfig` and fill in `AGENT_ADDRESS` and `INVITE_CODE`. That file is ignored by Git. Debug builds use it only when there is no saved pairing; a config pairing is locked like an accepted pairing. Release builds leave both bundled fields blank, so the distributed app carries no family's invite. The DEBUG-only `-uitest-unpaired` launch argument ignores saved/config pairings and uses a separate, reset test pairing store.

## Try it in the Simulator

Download `Whatcha-<version>-simulator.zip` from the [latest Release](https://github.com/openonion/whatcha-ios/releases/latest). Boot an iPhone simulator in Xcode, then run these commands in the download folder:

```sh
unzip Whatcha-*-simulator.zip
xcrun simctl install booted Whatcha.app
xcrun simctl launch booted ai.openonion.whatcha
```

Ask the child to issue a 口令 using the [Android RUNBOOK](https://github.com/openonion/whatcha-android/blob/wechat-look/RUNBOOK.md#the-commands) and send it in WeChat. Copy that message, open 在干嘛, and tap the big 「粘贴」 button. Then type a message and tap 发送.

From 0.2.2 the project archives for a real iPhone with an App Store icon, a privacy manifest and the export-compliance key, but it is not signed or submitted yet: building for a device needs your own Apple signing team. Releases so far provide source and a simulator build only; there is no App Store or TestFlight distribution yet. See the [privacy policy](PRIVACY.md). It is text only. Pairing by 口令 and chatting through the public relay were checked end to end on the simulator against a real family agent on 2026-11-08.

Until a 口令 is on the clipboard, the 「粘贴」 button is pale: iOS enables its paste control only when there is something to paste.

## Build and test

Open `Whatcha.xcodeproj`, or from the command line (simulator only, ad-hoc signed so the Keychain works):

```sh
xcodebuild test -scheme Whatcha -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  CODE_SIGNING_ALLOWED=YES CODE_SIGN_IDENTITY=- DEVELOPMENT_TEAM= AGENT_ADDRESS= INVITE_CODE=
swift test
```

The native macOS XCTest run exercises the same `Sources/WhatchaCore` and test files as the iOS test target. It does not verify the iOS screen, Keychain, or live relay. See [PLAN.md](PLAN.md) for round results and remaining acceptance checks.

The app keeps its lines, delivery states, title and session in one atomically written file. A pending message survives reopening. On reconnect, a completed answer in the host's `chat_items` is shown instead of asking again; a running turn is left alone. Questions go out one at a time. A grey circle means on its way; tapping a red ! retries that failed line. Connection retries wait 5, 10, 20, 40, 60 seconds, with a 10-second CONNECT deadline and an early retry when the app returns to the foreground.

M1 deliberately has text only. Voice, photos, read aloud, QR pairing and push are later work. The empty hint says 「打字就行」 only while the composer is shown.

The signature fixture was generated by `tools/AndroidWireVector.java` against the Android reference's compiled `Wire` and `Identity` classes, using the public test seed `00…1f`. `python3 tools/generate-vector.py` regenerates it after the Android debug build. The tests compare exact canonical payloads and verify both Android's fixture signatures and CryptoKit's generated signatures. CryptoKit randomizes Ed25519 signatures, so their bytes differ from Android's deterministic output; see [Apple's signature documentation](https://developer.apple.com/documentation/cryptokit/curve25519/signing/privatekey/signature(for:)). `tools/SwiftWireVector.swift` supports the reverse check with Android's canonicalizer and Bouncy Castle verifier. These tools never use an installed app or agent identity.

The owner runs a test agent with its own key. On an iPhone simulator: type 「在干嘛」, tap 发送, and check the Chinese answer, avatars, tails and title; then queue two questions offline, return to the app, retry a failure, and reopen after a completed answer. Verify only one INPUT for the recovered question in the host log. Check long answers, the keyboard, scrolling and large text separately. These checks are still required before M1 is accepted.
